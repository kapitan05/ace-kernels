1. The loss, and why the original is slow

Concept: what mL1-ACE measures

A segmentation network outputs, for every voxel and class, a probability p. A model is calibrated when its confidence matches reality: of all voxels predicted with probability ~0.8 for "kidney", ~80% really are kidney. The average calibration error (ACE) measures the gap:

  1. Split the probability range [0, 1] into K bins (K = 20 in the paper).
  2. Put every voxel into the bin of its probability.
  3. Per bin: compare the mean predicted probability with the fraction of voxels that really belong to the class (mean of the 0/1 target).
  4. Average the absolute gaps over the non-empty bins: that is the loss for one (volume, class) pair. mL1-ACE then averages over classes (and the batch).

For one (b, c) pair with bins k = 1..K, voxel sets B_k, n_k = |B_k|:

f_bc = mean over non-empty k of | (1/n_k) sum_{i in B_k} p_i  -  (1/n_k) sum_{i in B_k} y_i |

Hard binning puts each voxel in exactly one bin, as above. Soft binning spreads each voxel over its two nearest bin centres with linear weights, so the loss is smooth in p (gradients do not jump when a voxel crosses a bin edge). Everything below comes in both variants.

Why it is slow: memory-bound work done the expensive way

The loss does very little arithmetic per voxel, so the ideal implementation is memory-bound: its time is set by how fast the GPU can read the inputs. On a T4 (320 GB/s), reading the kits23 batch (2 x 4 x 128^3 float32 logits + labels) once for the forward and twice for the backward takes ~0.8 ms. That is the bandwidth floor. The original takes ~100 ms (hard) / ~180 ms (soft): 118x / 217x above the floor.

Where do 100 ms go? The profiler (Sprint 2) answered it, and the answer was not the obvious one:

Atomic contention. An atomic add makes a read-modify-write on one memory address indivisible. When millions of GPU threads atomically add into the same 20 addresses, they serialize: the hardware handles colliding updates one after another. The fix (page 4) is to let each block of threads build a private histogram in its own registers and publish it with one atomic per bin.

GPU-bound, launch-bound or sync-bound? How we diagnosed it

A program on a GPU is slow for one of three reasons. Which one decides the fix:

regime what happens timeline looks like fix
GPU-bound the CPU queues kernels quickly, then waits; the GPU runs them back to back GPU row full, no gaps better kernels: less memory traffic, fusion, a better algorithm, lower precision
launch-bound (CPU / CUDA-API bound) each kernel is so small that the GPU finishes it before the CPU has launched the next gaps between GPU kernels fewer, bigger kernels: fusion, CUDA graphs, torch.compile, bigger batches
sync-bound CPU and GPU take turns: .item(), .cpu(), a host-to-device copy, data-dependent Python if both rows with gaps, alternating remove syncs, keep data on the GPU, overlap

Launch cost is at least ~5 us of CPU time per kernel, so kernels x 5 us is a lower bound on the time of a call no matter how fast the GPU is: the launch floor (launch_floor_ms in every benchmark row). It is optimistic: an eager PyTorch op also costs Python and dispatcher time (measured below: ~15 us per kernel for the original), so a launch-bound call sits within a few x of the floor, while a GPU-bound call is tens of x above it.

A torch.compile speedup does not prove "launch-bound"

torch.compile changes three things at once: (1) it merges kernels, which removes launches (helps only if launch-bound); (2) it fuses chains of elementwise ops into one kernel that reads its inputs once and keeps intermediates in registers, cutting DRAM traffic (helps a memory-bound GPU workload, even with zero launch overhead); (3) it generates different code for some ops. For the original loss, (2) is where the gain comes from: soft binning is a long chain of elementwise ops on voxel-sized temporaries (11x the input), and fusing it saves bytes, not launches. Knowing that compile helped tells you something was wasteful; it does not tell you what. Four tests do.

Test 1: launch floor vs measured time, and Test 2: a CUDA graph

A CUDA graph records a sequence of kernels once and replays it with a single launch: it removes only the launch cost. If a call gets faster in a graph, it was launch-bound; if not, it was not. The harness measures every case both ways (cuda_graph: true in the config adds the graphed row):

Test 4: shrink the input

GPU work shrinks with the data; launch cost does not. So as the input gets smaller, a GPU-bound call gets faster, and a launch-bound call stops getting faster at its launch floor. Sprint 11 measured the four deep-supervision sizes of the paper's network (experiment sprint11-deepsup, config bench/configs/sprint11_deepsup.yaml):

  • Original at 128^3: 47.5 ms with or without a graph: GPU-bound.
  • Original at 16^3: 3.7 ms eager, 1.2 ms in a graph: the same code is launch-bound at small sizes (~230 launches at batch 1; the graph removes their CPU cost and lands at the launch floor, 1.16 ms).
  • v5 (Sprint 8): ~0.85-0.9 ms from 64^3 down to 16^3, flat, and a graph cuts it to 0.15 ms: launch-bound (~55 launches). This finding led to Sprint 11's fused epilogue: v6 has 7 launches and falls to 0.034 ms at 16^3, with or without a graph.

Self-check: torch.compile made the original soft loss 4.7x faster. Does that mean it was launch-bound?
No. Its launches cost ~5 ms of 184 ms. Compile fused a long chain of elementwise ops on voxel-sized temporaries, so the GPU moved far fewer bytes: a GPU (memory) win. The CUDA-graph test is the clean check for launch overhead.
Self-check: The same code is GPU-bound at 128^3 and launch-bound at 16^3. How?
Launch cost is fixed per kernel (~5 us x kernels); GPU work scales with the data. At 16^3 the data is 512x smaller, the GPU work drops below the launch cost, and the launches dominate.
Self-check: Which two numbers in a benchmark row tell you the regime without any profiler?
p50_ms and launch_floor_ms (= kernels_per_call x 5 us). Within a few x: launch-bound (the floor is optimistic). Tens of x apart: GPU-bound. Confirm with the graphed row: a launch-bound call drops to about the floor.

Evidence

Self-check: Why does removing the Python loop over B x C barely help (1.2x)?
The loop only adds kernel launches (~5 us each); the time is spent inside the scatter kernels, where millions of atomics collide on 20 addresses. Fewer, bigger scatters still collide.
Self-check: Why does a CUDA graph not speed up the original hard loss?
A CUDA graph removes CPU launch overhead. The original is not launch-bound but GPU-bound (atomic contention), so there is nothing for the graph to remove.
Self-check: What is the bandwidth floor of kits23 forward + backward on a T4?
Ideal bytes = 2 x (input + target) + input (read twice, write the gradient once) ~ 268 MB; 268 MB / 320 GB/s ~ 0.84 ms.
