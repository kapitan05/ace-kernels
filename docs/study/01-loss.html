1. The loss, and why the original is slow

Concept: what mL1-ACE measures

A segmentation network outputs, for every voxel and class, a probability p. A model is calibrated when its confidence matches reality: of all voxels predicted with probability ~0.8 for "kidney", ~80% really are kidney. The average calibration error (ACE) measures the gap:

  1. Split the probability range [0, 1] into K bins (K = 20 in the paper).
  2. Put every voxel into the bin of its probability.
  3. Per bin: compare the mean predicted probability with the fraction of voxels that really belong to the class (mean of the 0/1 target).
  4. Average the absolute gaps over the non-empty bins: that is the loss for one (volume, class) pair. mL1-ACE then averages over classes (and the batch).

For one (b, c) pair with bins k = 1..K, voxel sets B_k, n_k = |B_k|:

f_bc = mean over non-empty k of | (1/n_k) sum_{i in B_k} p_i  -  (1/n_k) sum_{i in B_k} y_i |

Hard binning puts each voxel in exactly one bin, as above. Soft binning spreads each voxel over its two nearest bin centres with linear weights, so the loss is smooth in p (gradients do not jump when a voxel crosses a bin edge). Everything below comes in both variants.

Why it is slow: memory-bound work done the expensive way

The loss does very little arithmetic per voxel, so the ideal implementation is memory-bound: its time is set by how fast the GPU can read the inputs. On a T4 (320 GB/s), reading the kits23 batch (2 x 4 x 128^3 float32 logits + labels) once for the forward and twice for the backward takes ~0.8 ms. That is the bandwidth floor. The original takes ~100 ms (hard) / ~180 ms (soft): 118x / 217x above the floor.

Where do 100 ms go? The profiler (Sprint 2) answered it, and the answer was not the obvious one:

Atomic contention. An atomic add makes a read-modify-write on one memory address indivisible. When millions of GPU threads atomically add into the same 20 addresses, they serialize: the hardware handles colliding updates one after another. The fix (page 4) is to let each block of threads build a private histogram in its own registers and publish it with one atomic per bin.

Other waste found in Sprint 2 (each fixed by a later sprint):

Evidence

Self-check: Why does removing the Python loop over B x C barely help (1.2x)?
The loop only adds kernel launches (~5 us each); the time is spent inside the scatter kernels, where millions of atomics collide on 20 addresses. Fewer, bigger scatters still collide.
Self-check: Why does a CUDA graph not speed up the original hard loss?
A CUDA graph removes CPU launch overhead. The original is not launch-bound but GPU-bound (atomic contention), so there is nothing for the graph to remove.
Self-check: What is the bandwidth floor of kits23 forward + backward on a T4?
Ideal bytes = 2 x (input + target) + input (read twice, write the gradient once) ~ 268 MB; 268 MB / 320 GB/s ~ 0.84 ms.
