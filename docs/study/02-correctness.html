2. Proving "same as the original"

A faster loss is worthless if it computes something else. This page shows the layers of evidence that every implementation returns the same loss and the same gradient as the upstream code, and how "same" is defined for floating point.

Concept: five independent layers

layer question it answers where
frozen reference is our ground truth really the upstream code? tests/test_reference_frozen.py
independent oracle does the upstream code compute the paper's formula? tests/oracle.py, test_oracle.py
golden files + 43 cases does every implementation match the reference on curated edge cases? tests/golden/, test_golden.py
random equivalence ... and on random shapes, classes, bins, options? test_equivalence.py (hypothesis)
full-size output check ... at real training sizes on the GPU, vs a float64 truth? ace_bench/measure.py

Plus targeted tests per technique: gradcheck of the handwritten backward (test_v2.py), exact bin counts and kernel-vs-PyTorch statistics (test_triton.py), the drop-in module against the upstream classes (test_module.py), no host syncs and CUDA-graph capture (test_sync.py), memory saved for backward (test_saved_tensors.py). No benchmark of an implementation runs unless all of these pass (the Kaggle job's first step is the full test suite).

Tolerances: why these numbers

Why not demand exact equality? Floating-point addition is not associative: (a + b) + c and a + (b + c) can differ in the last bit. Every implementation sums the same values in a different order (a Python loop, one big scatter, tree sums inside a Triton block, atomics in a random order), so two correct implementations differ by rounding. fp32 has 24 significant bits: one rounding is ~6e-8 relative (eps32 / 2), and a loss built from sums of thousands of values accumulates a few of those. A tolerance must be above this legitimate noise and far below what any real bug produces. Each constant was set by measuring both sides:

constant value legitimate noise (measured) why this value
LOSS_RTOL 1e-5 relative the reference vs the float64 oracle: ~1e-7..1e-6 on test sizes ~10x headroom over fp32 noise; a 1e-4 change in one bin edge already exceeds it (below)
LOSS_ATOL 1e-6 absolute for losses near 0 (a relative tolerance of a tiny number is meaningless)
GRAD_RTOL 1e-4 relative (CPU) ~2e-7 on test cases gradients involve divisions by bin weights, so a little more room than the loss
GRAD_ATOL 1e-7 absolute gradient entries that should be ~0
CUDA_GRAD_RTOL 1e-3 relative (GPU vs CPU golden) 3.5e-4 worst case, measured on a T4 soft binning with only ~3 voxels in a bin: its gradient is the difference of two nearly equal terms, which amplifies ~1e-7 rounding ~1000x; 1e-3 is the next round number above
CUDA_GRAD_ATOL 1e-6 absolute as above, for near-zero entries

Too loose would hide bugs; too tight would fail correct code. The check that the constants are not too loose: deliberately broken versions (mutants) of the math must fail them. The worked example below compares three correct implementations with the float64 truth, then three subtle bugs (mutants of the formula):

The correct implementations differ from the truth by ~1e-8..1e-7; the first two mutants change the loss by 5e-3..1e-1, 500-10000x the tolerance: it sits safely between legitimate noise and real bugs. The third mutant changes nothing on random inputs, because no random probability lands exactly on a bin edge, where right matters. That is why the golden cases include inputs placed exactly on the edges (bin-edges-left, bin-edges-right): some bugs are invisible to random testing and need constructed edge cases.

Ties are the other special case. The loss contains |mean p - mean y|; where a bin's difference is exactly 0, the derivative is undefined (a kink) and any value in [-1, 1] is a valid subgradient. Eager PyTorch returns 0; a compiled kernel that reorders float ops gets +-1e-9 and returns +-1/N. Both are right; the tests treat these tie cases specially:

The measurement harness: ace_bench/measure.py

Unit tests use tensors of a few thousand voxels. The real question is whether an implementation is right, fast and lean at training size, on the GPU. measure.py answers that for one combination at a time: it turns (implementation, binning, shape, mode, CUDA graph or not) into one result row (Row, page 7) with time, bandwidth, launches, memory and accuracy. Everything in the benchmark tables of this guide is a set of such rows.

How it fits together (one benchmark config -> many rows):

run.py      for each (shape, binning, implementation): a fresh worker process

                  measure_case(...)  -> Row   build input, check, count, measure
              release_memory()               between rows
            -> rows.parquet, summary.md, plots

Worked example: why max-norm gradient errors mislead

At full size, the max-norm gradient error (largest relative difference of any single element) of correct implementations can reach 0.5. The reason is the |x| kink: in a bin whose mean p and mean y almost cancel, the sign of the difference decides the gradient of all its voxels, and the sign depends on summation order:

Same data, two correct fp32 summation orders: one says the gap is positive (every voxel in the bin gets gradient +1/n), the other says exactly 0 (subgradient 0). The gradient of every voxel in such a bin differs completely between two correct implementations. The relative L2 error of the whole gradient (one number over all voxels) is the meaningful accuracy measure; the max-norm stays as a diagnostic.

Why the original is less accurate than ours

How it was found

  1. Sprint 7 (5423f09): every benchmark row started comparing its output with the reference at full size. Our kernels differed from the reference by up to ~1e-5 in the loss and "0.5" in the max-norm gradient error at large volumes. With two fp32 results, you cannot tell which one is wrong.
  2. Between Sprints 7 and 8 (8cecf92, verify run results/kaggle/47c938da465d-run-verify/): a third, much more precise opinion was added: the float64 truth (Step 1 above). Result: the reference was the one further from the truth in the loss; our Triton versions were 10-100x closer. The max-norm gradient errors turned out to be large for every implementation, the reference included (the |x| kink, worked example above).
  3. Sprint 9 (55b7d1a, verify run results/kaggle/55b7d1a680c0-run-verify/): the L2 gradient error was added: all implementations have the same L2 error as the reference (~1e-4).
  4. Sprint 11 (realistic inputs, results/kaggle/6ad66a182fc4-run-sprint11-precise/): on trained-network-like inputs (peaked, mostly correct softmax) the reference's loss is 2e-3 off the float64 value; ours 1e-7..6e-6.

Why: how each implementation adds up a bin

The loss needs, per bin, the sum of the probabilities of its voxels. The original uses scatter_add / scatter_reduce: on the GPU, every voxel's value is atomically added to one running total per bin. Each addition rounds to fp32 against a total that keeps growing, so the error grows with the number of voxels in the bin (like adding pennies to a huge balance: eventually each penny is partly rounded away).

Our kernels first add BLOCK (128-512) values inside a program as a tree (pairs, then pairs of pairs: only ~log2(BLOCK) = 8-9 roundings deep), and only the block's partial sum is added to the running total: 256x fewer additions to the big number.

On peaked, realistic inputs ~70% of all voxels fall into bin 0 (probabilities near 0), so that one bin holds millions of values: the worst case for the running total. The same effect, reproduced on the CPU with 2M values of a typical bin 0:

The relative error of a bin's mean probability then propagates into the loss: the loss is the difference mean p - mean y per bin, often much smaller than either mean, so a small relative error in mean p becomes a larger relative error in the loss (that is how 1.4e-4 in a sum becomes 2e-3 in the loss on realistic inputs).

Was it "fixed"?

The original is frozen (it is the ground truth for what is computed, not for how precisely), so it was not changed. Ours is more accurate as a side effect of the privatized histograms (page 4), and that is now guarded: a test requires the Triton statistics to be within 1e-5 of the float64 truth and never meaningfully worse than PyTorch's own fp32 result:

The benchmark harness re-checks the same at full size in every row (Step 3 above), and the report flags any implementation whose error exceeds 2x the reference's own. Two intermediate PyTorch steps were flagged that way (v1_clean_compile, v2_recompute, soft, up to 7.5e-5 at 256^3: one scatter_add over all slices accumulates even more into each running total); the final Triton versions are not.

Self-check: Golden files prove "same as the reference". What does the oracle add?
Independence: the reference could itself be wrong (or both could share a bug, e.g. if we had copied its code). The oracle is written from the paper's formula in float64, so it validates the ground truth.
Self-check: Why is a gradient tolerance of 1e-3 on CUDA acceptable and not hiding bugs?
It was set from measurement (worst legitimate case 3.5e-4: few voxels per bin amplify rounding) and checked against mutants, which were off by >= 1%. A real bug moves gradients by far more than 1e-3.
Self-check: Why can the original be 2e-3 off on realistic inputs while ours is 1e-6?
The original adds every voxel to one running fp32 total per bin (atomics); with millions of voxels in bin 0 the rounding accumulates. Ours adds blocks of 256 as trees first and then only the block totals: ~256x fewer additions to the big total.
Self-check: What does measure_case do after timing, and why after?
The output check (loss and gradient vs the reference and float64 truth). After timing, so the extra work and memory do not distort the time and peak-memory numbers.
Self-check: An implementation has max-norm gradient error 0.5 vs the reference. Is it wrong?
Not necessarily: look at the L2 error vs float64 and compare with the reference's own error vs float64. If both are equal (~1e-4), the 0.5 comes from sign flips in near-tie bins, which both fp32 implementations suffer.
