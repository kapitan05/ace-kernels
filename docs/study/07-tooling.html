7. Tooling: benchmark harness, Kaggle, W&B, profiler

The results on the other pages are only as trustworthy as the measurement. This page explains the machinery that produced every number, and the bugs it had.

The workflow of one experiment

  1. Write a config with a hypothesis (YAML, validated by pydantic).
  2. Commit; submit a Kaggle job: a snapshot of the commit runs on a T4, starting with the full test suite (the gate).
  3. The benchmark harness runs every (shape, binning, implementation) group in a fresh process and writes rows.parquet, summary.md, plots.
  4. Fetch the results into results/kaggle/<commit>-<job>/; mirror to W&B.
  5. Write the report section; rebuild the ablation table; tag the sprint in git.

Remote GPU: Kaggle from the command line

No notebook: ace_bench.remote uploads a git archive of the current commit as a private Kaggle dataset, pushes a script kernel with a T4, polls its status and downloads results.tgz:

Every job script starts with the same setup: GPU check, locked environment (uv sync --frozen), then the correctness gate:

$ uv run python -m ace_bench.remote submit kaggle/run_sprint11.sh --no-wait

push the job; then ... remote status kaggle/run_sprint11.sh and ... remote fetch kaggle/run_sprint11.sh

Experiment tracking: W&B

Parquet files in git-ignored results/ are the source of truth; W&B (project ace-kernels) is the shareable mirror: one W&B run per benchmark run, grouped by sprint, with the config, hypothesis, environment, the row table, plots and profiles. API keys only come from the environment, never from code:

Profiler and memory snapshots

ace_bench.profile records three steps with torch.profiler (kernel names and GPU time per kernel, trace.json for ui.perfetto.dev), the tensors saved for backward, and a CUDA memory snapshot for pytorch.org/memory_viz (allocation timeline: you see the original's per-voxel tensors pile up and ours not). ncu (hardware counters) is blocked on Kaggle, so occupancy and DRAM-byte counters wait for the RTX PRO 6000.

Bugs in the tooling (and what they teach)

bug symptom fix
saved-tensor pack hook returned the tensor itself reference cycle, GPU memory leak, 38 false OOM rows return t.detach(); process isolation
pytest ... \| tail -1 a failing suite looked green (tail's exit code) set -o pipefail everywhere
grid axis 1 = voxel blocks "invalid argument" at 256^3 (limit 65535) blocks on axis 0 + regression test
first shape of a run slower for all Triton kernels v6_index looked slower than v5 at kits23 cross-check in a second run; noted in the report
float atomics compared bit-exactly in a test false failures (order of atomic adds varies) exact counts, sums within rounding

Self-check: Why does every benchmark group run in its own process?
So one group's failure (CUDA error, OOM, leak) cannot change the next group's measurements; and peak-memory numbers start from a clean allocator.
Self-check: Why is the time measured with CUDA events and an L2 flush instead of time.time()?
GPU calls are asynchronous (Python returns early); events time the GPU work itself. The L2 flush makes each repetition read from DRAM, as in training, instead of from a warm cache.
Self-check: Where do you find the exact code that produced a number in the report?
The run folder name starts with the commit hash (results/kaggle/<commit>-<job>/), the snapshot has a COMMIT file, and every row has run_id and the env (GPU, versions, git sha).
