3. PyTorch: vectorize, then write the backward by hand

Before writing GPU kernels, two questions are answered in plain PyTorch: how much does removing the Python loop give (Sprint 3, v1), and how much memory does a handwritten backward save (Sprint 4, v2)? Both versions also become references for the kernels: v2's math is exactly what the Triton kernels compute.

v1: one scatter for all slices instead of B x C loops

Concept. The loop over (batch, class) launches 3 scatters per slice. Instead, give every (b, c) slice its own block of K bins in one flat buffer of size BCK: voxel i of slice r goes to flat bin r*K + bin(p_i). One scatter then handles all slices at once.

v1_clean then removes the remaining waste: sums instead of scatter_reduce(mean) (means are computed per bin afterwards), no one-hot target copy (class indices are used directly), no host-device synchronization. The shared statistics function:

Result. Removing the loop alone: 1.2x. The cleanup: 2.6x. With torch.compile on top: ~5x. Still under 5% of the hardware limit, because the scatters (atomics) remain. This was the evidence that the next step had to be a custom kernel.

v2: deriving the backward

Concept. Autograd stores whatever the forward computed per voxel (bin indices, one-hot targets, gathered means) to replay it backwards: 3x the input (hard), 11x (soft). But the loss only depends on per-bin sums, so the gradient can be written in terms of tiny per-bin tensors. From docs/derivation.md:

d_k = P_k / W_k - G_k / W_k                   (mean p minus mean y in bin k)
df/dp_i = sum over bins j of voxel i:  s_kj / (K_ne W_kj) * [ w_ij + w'_ij (p_i - y_i - d_kj) ]

with s_k = sign(d_k), K_ne = number of non-empty bins, w the bin weight of the voxel and w' its derivative. For hard binning w = 1, w' = 0, so every voxel in bin k gets the same gradient:

df/dp_i = sign(d_k) / (K_ne * W_k)        =: coef_k

The backward therefore needs only coef and d: two [B, C, K] tensors (640 bytes for B=2, C=4, K=20), plus the inputs that the caller holds anyway. It recomputes each voxel's bin from p instead of storing it.

Self-check: Why can the backward recompute bins instead of storing them, and what does it cost?
Bins depend only on p (and the fixed edge table), which the backward has anyway. The cost is reading p again and re-binning: cheap compared with storing and reading back int64 indices (8 bytes per voxel per class).
Self-check: What is the gradient of a voxel in an empty bin, and in a bin with d_k = 0?
Empty bin: the voxel cannot be in it (empty means no voxels for hard binning); for soft, weights below empty_weight -> coef 0. d_k = 0: sign(0) = 0, so gradient 0, the same subgradient eager PyTorch's abs backward returns.
Self-check: grad_in_fwd saves 1x the input. When is it better than recompute?
When backward speed matters more than memory: the backward becomes a multiply. It was not used later because the Triton backward (one pass, no stored gradient) gives both.
